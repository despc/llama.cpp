> ## About this fork / О форке
>
> **EN.** This fork adds a `V100_CUDA` backend, so a Tesla V100 can serve a model
> together with consumer GPUs inside a single `llama-server` process.
>
> The V100 needs the proprietary NVIDIA driver, while the RTX 5080 / 5070 Ti need
> the open one. Two kernel modules already coexist; the problem is user space.
> Both drivers ship a `libcuda` with the same SONAME, so the dynamic loader keeps
> only one copy and whichever loads first ends up serving every GPU. This fork
> copies the V100 driver stack under distinct `libcv*` names, builds a second CUDA
> backend against it, and keeps its symbols private. A small `LD_PRELOAD` shim
> sends that stack's device opens to `/dev/nvidia-v100-*`.
>
> The result is a normal local device, `V100_CUDA0`, usable with `--device` and
> `--tensor-split` next to `CUDA0` / `CUDA1`. It replaces the older workaround of
> running the V100 behind an RPC server in a separate process.
>
> Everything lives in [`ggml/src/ggml-v100-cuda/`](ggml/src/ggml-v100-cuda/) - see
> its README for build and run instructions. Changes to shared llama.cpp code are
> deliberately kept to a handful of additive lines.
>
> **RU.** Форк добавляет бэкенд `V100_CUDA`: Tesla V100 работает над моделью
> вместе с потребительскими картами в одном процессе `llama-server`.
>
> V100 требует проприетарный драйвер NVIDIA, а RTX 5080 / 5070 Ti - открытый. Два
> модуля ядра уживаются и так, сложность в пользовательском пространстве. У обоих
> драйверов `libcuda` с одинаковым SONAME, поэтому загрузчик оставляет только одну
> копию, и первый загрузившийся драйвер обслуживает все карты. Форк копирует
> драйверный стек V100 под именами `libcv*`, собирает против него второй CUDA
> бэкенд и прячет его символы. Небольшая `LD_PRELOAD` библиотека направляет
> обращения этого стека к `/dev/nvidia-v100-*`.
>
> В итоге получается обычное локальное устройство `V100_CUDA0`, доступное в
> `--device` и `--tensor-split` наравне с `CUDA0` / `CUDA1`. Это заменяет прежний
> обходной путь, когда V100 работала через RPC-сервер в отдельном процессе.
>
> Всё лежит в [`ggml/src/ggml-v100-cuda/`](ggml/src/ggml-v100-cuda/), там же README
> со сборкой и запуском. Правки в общем коде llama.cpp намеренно сведены к
> нескольким добавленным строкам.
>

> ## Что здесь ускоряли
>
> Четыре карты разной скорости считают одну модель вместе: RTX 5080, RTX 5070 Ti
> и две Tesla V100. Прямой связи между ними нет — теслы живут за отдельным
> драйверным стеком, — поэтому каждый байт, которым карты обмениваются, дважды
> пересекает PCIe через оперативную память хоста. На Qwen3.8-27B в тензорном
> режиме на этот обмен уходило около 90% времени префила: узким местом были не
> вычисления, а пересылки.
>
> Результат на одном и том же запросе (1430 токенов на входе, 200 на выходе):
>
> | | было | стало |
> |---|---:|---:|
> | префил | 187 т/с | **630 т/с** |
> | генерация | 63 т/с | **78 т/с** |
>
> Всё, что осталось включённым, проверено поэлементным сравнением с эталонной
> свёрткой — 965 миллионов элементов на карту, ноль расхождений. Ничего из
> ускорений не меняет арифметику: точность не разменивалась ни разу, это было
> условием работы.
>
> ### Что именно сделано
>
> **Дерево сложения как у эталона.** Свёртка складывает вклады карт в том же
> порядке и с тем же округлением, что и штатный мета-бэкенд. Это не ускорение
> само по себе, но благодаря ему любое дальнейшее изменение можно проверять
> побитовым сравнением, а не «на глаз».
>
> **Reduce-scatter вместо полной свёртки у всех.** Раньше каждая карта тянула к
> себе вклады всех остальных и складывала всё целиком. Теперь каждая сводит
> только свою долю, а потом карты обмениваются готовыми долями. Трафика 2.75N
> вместо 4N.
>
> **Публикация порциями.** Карта не ждёт, пока запишет весь свой вклад, а
> объявляет его частями — соседи начинают читать раньше.
>
> **Своя доля не публикуется.** Область, которую карта сводит сама, никто у неё
> не читает, а раньше она всё равно отправлялась по шине.
>
> **Неравные доли свёртки.** Теслы медленнее на обмене, поэтому сводят меньшую
> часть: 35/35/15/15 вместо поровну.
>
> **Участие по слоям — самое крупное.** Раньше каждый слой резался на все четыре
> карты, и каждый слой заканчивался обменом между всеми четырьмя. Теперь
> большинство слоёв делит между собой только пара блэкволлов, а теслы владеют
> двенадцатью слоями целиком — вдвоём на слой. Карта без доли в слое не публикует
> ничего, её никто не ждёт, и она не участвует в свёртке этого слоя. Только это
> дало префилу прирост с 370 до 630 т/с.
>
> **Какие слои отдавать теслам, решает память, а не скорость.** Слой стоит около
> 0.45 ГиБ, а слой с KV-кешем — ещё гигабайт при большом контексте, и KV есть
> только у каждого четвёртого. Поэтому теслам отдаются именно слои с KV: так
> блэкволлы, у которых всего по 16 ГиБ, помещают 49 слоёв вместо 40.
>
> ### Что попробовали и отвергли
>
> Примерно половина работы — измеренные отказы. Они записаны так же подробно,
> как и удачи, чтобы к ним не возвращались по кругу:
>
> - **Дуплекс** — гонять обмен в обе стороны разом. Линия это умеет (замерено,
>   1.34x), но чтобы этим воспользоваться, коллектив надо резать на части, а
>   каждая часть добавляет круг синхронизации между картами. На картах, которые
>   различаются в 1.7 раза по скорости, круг стоит дороже, чем даёт перекрытие.
> - **Прямой обмен между картами (P2P)** — у тесл 1.38 ГБ/с против 3.29 через
>   хост, у блэкволлов недоступен вовсе.
> - **Больше блоков в ядре свёртки** — ноль пользы: каждая фаза и так насыщает
>   линию в своём направлении.
> - **Пропуск слоёв на картах, которые в них не участвуют** — реализовано,
>   корректно, убирает 3.35 ГиБ обмена из 3.81, и всё равно медленнее: передача
>   готового выхода слоя требует своей точки синхронизации, а она дороже.
> - **Перестановка карт по слотам** — расчёт дал ровный ноль.
>
> Общий вывод из всех отказов один: этот обмен упирается не в то, **сколько**
> карты пересылают, а в то, **как часто им приходится договариваться**.
>
> ### Где что лежит
>
> Подробный дневник со всеми числами и неудачами —
> [`docs/backend/CUDA-mixed-runtime-allreduce.md`](docs/backend/CUDA-mixed-runtime-allreduce.md).
> Настройки запуска (доли, размещение слоёв, контекст) — в пусковых скриптах
> рядом с бинарём, там же записаны замеры, по которым числа выбирались.
>
> Полезное для проверки: `GGML_CUDA_MIXED_AR_VERIFY=1` сверяет каждый коллектив
> с эталонной свёрткой поэлементно, `GGML_CUDA_MIXED_AR_PROFILE=1` показывает,
> куда уходит время и сколько байт пересылается по видам обмена.

> ## Вторая модель: Qwen3.8-Flash-Next
>
> Она работает иначе — слои раздаются картам целиком, а не режутся между ними,
> поэтому ничего из описанного выше к ней не относится: обмена между картами
> почти нет, и узкое место другое. Модель разрежённая (MoE), и почти всё время
> префила уходит на матрицы экспертов.
>
> Здесь выигрыш дали не пересылки, а **выбор ядер под Volta**. У V100 нет
> тензорных инструкций, которые появились в Turing, а правила выбора ядра в
> llama.cpp их наличие подразумевают. Из-за этого теслы сваливались в запасные
> пути, заметно худшие.
>
> Три исправления, все — про выбор ядра, ни одно не меняет арифметику:
>
> **Групповой квантованный `MUL_MAT_ID`.** Каждая проекция эксперта на префиле
> уходила в запасной путь, синхронизирующийся с хостом: 284 тысячи запусков ядер
> на один префил в 5000 токенов, и CUDA-граф при этом не собирался вовсе.
> 478 → 613 т/с.
>
> **Правильная таблица тайлов DP4A.** Для Volta выбиралась таблица, рассчитанная
> на другую раскладку вычислений. 613 → 811 т/с.
>
> **Тайл по столбцам на эксперта.** При 512 экспертах каждому в микробатче
> достаётся горстка токенов, а тайл рассчитывался на весь батч — то есть считался
> в основном на пустом месте. Ограничено раскладкой DP4A: на блэкволловской MMA
> то же правило почти весь выигрыш съедало. 811 → 907 т/с.
>
> Вместе на развёрнутой сборке при промпте 10 тысяч токенов: **460 → 830 т/с**
> префила, то есть в 1.8 раза. На генерацию не влияют совсем — декод идёт другим
> путём, где это правило не работает.
>
> **Вывод байт в байт совпадает** с версией без этих исправлений — проверено
> трижды, включая прямое A/B на одном промпте с генерацией в 3000 токенов. Именно
> поэтому их и вернули: правило форка исключает всё, что может переставить
> арифметику, а здесь переставлять нечего. Флаги
> `GGML_CUDA_MMID_MMQ_PREFILL=0` и `GGML_CUDA_MMQ_MMID_J_FIT=0` позволяют
> проверить это заново. У третьего исправления флага нет и быть не может: хост
> выбирает конфигурацию запуска, а устройство — по `__CUDA_ARCH__` на этапе
> компиляции, и переключатель во время работы их бы рассинхронизировал.
>
> ### Что отвергли здесь
>
> - **Компактное внимание** — давало 23% на 100 тысячах токенов и 34% на 150
>   тысячах, ускоряло и декод. Удалено: оно меняло численные результаты и
>   выдаваемый текст. Разница перплексии 0.048% не является границей потери
>   качества, а совпадение 21 из 24 позиций декода ничего не гарантирует для
>   остальных предсказаний. Правило простое: вариант, способный ухудшить точность
>   хотя бы теоретически, не рассматривается.
> - **Микробатч 640** — примерно 7% префила ценой 4% генерации после 150 тысяч и
>   лишних 284–350 МиБ на карту. Оставлен 512.
> - **Два слота конвейера копирования** — выигрыш около 0.5%, при этом запрос на
>   30 тысяч токенов не помещался в память.
> - **FP16 для экспертов** — выигрыша не показал, а проблему, ради которой
>   затевался, закрыли исправления выравнивания и диспетчеризации.
>
> Прототип компактного внимания попутно вскрыл настоящие ошибки — в размере
> выделения, форме эталонной маски, шаге индекса, времени жизни захваченного
> буфера и в проверке на бесконечности. Их исправили до удаления. Урок, который
> из этого вынесли: проверять промежуточные данные и поведение захвата графа, а
> не доверять правдоподобному выводу и скорости.
>
> Подробности и полная кривая по длинам контекста —
> [`docs/backend/CUDA-flash-next-prefill-plan.md`](docs/backend/CUDA-flash-next-prefill-plan.md).

> ## Flash-Next, сентябрь 26–29: конвейер, драфт и top-k
>
> После исправления ядер узким местом стали не вычисления, а то, как четыре
> карты друг друга ждут. Модель идёт конвейером: 5080 → 5070 Ti → SXM2 → PCIe, и
> к ней приставлен MTP-драфт для спекулятивной генерации, который живёт на
> PCIe-тесле. Эту часть работы вели по профилю: таймлайн по картам, лог ожиданий
> планировщика, метки хоста — и каждое найденное ожидание разбирали до причины.
>
> Итог на той же машине и том же лаунчере (контекст 160 тысяч). «До» — префил
> 27 сентября (уже с таблицей PLE в памяти, без неё было ещё вдвое хуже),
> генерация — утро 28 сентября:
>
> | | до | сейчас |
> |---|---:|---:|
> | префил, промпт 10 тыс. | 864 т/с | **1932 т/с** |
> | префил, 30 тыс. | 742 т/с | **1913 т/с** |
> | префил, 100 тыс. | ~475 т/с | **1307 т/с** |
> | префил, 150 тыс. | 377 т/с | **1070 т/с** |
> | генерация после промпта 30 тыс. | 49 т/с | **58 т/с** |
> | генерация, короткие промпты (5 задач, ru/en/код) | 77.5 т/с | **84 т/с** |
> | генерация при переписывании кода: MTP → MTP + ngram-mod | 104 т/с | **126 т/с** |
>
> ### Префил: конвейер больше не останавливается
>
> **Таблица PLE в памяти** (`--lazy-mode off`). Таблица per-layer-эмбеддингов —
> 26.8 ГиБ, и при чтении по требованию каждый новый текст ловил сотни тысяч
> промахов страниц с NVMe: 450 т/с на холодном кеше против 850 на тёплом. Теперь
> она читается в RAM при старте. Заодно `vm.swappiness=10`, чтобы её не
> вытесняло в своп.
>
> **Микробатчи одной формы** (`LLAMA_KV_PAD_PREFILL=4096`, `LLAMA_REUSE_NOSYNC`,
> `GGML_CUDA_GRAPH_ALWAYS_CAPTURE`, `LLAMA_PREFILL_NO_REUSE`, два слота копий у
> тесл). Карты шли строго по очереди: каждый микробатч заново планировал граф и
> ждал все четыре карты. Теперь восемь микробатчей батча имеют одну форму, граф
> захватывается целиком, слоты копирования чередуются — префил +58–63%.
>
> **Ленивая синхронизация при перестройке графа**
> (`GGML_SCHED_LAZY_REALLOC_SYNC`). На границе каждого батча в 4 тысячи токенов
> длина KV вырастает, граф перестраивается, и планировщик синхронизировал все
> карты — 440 мс простоя на батч, пока теслы дорабатывали предыдущий. Буферы при
> этом не растут (зарезервированы по худшему случаю при старте), поэтому теперь
> каждая карта ждёт только свою прошлую работу перед своим первым шагом нового
> графа. Без драфта: 30 тыс. 1645 → 1790 т/с.
>
> **Копирования между картами — в отдельных потоках** (`GGML_CUDA_COPY_OVERLAP`).
> Точный таймлайн (на CUDA-событиях, `GGML_CUDA_TIMELINE_EVENTS=1`: прежний, на
> host-callback'ах, сам тормозил V100 и показывал неправду) показал, что загрузка
> входа на SXM2 стояла в очереди за её же вычислениями, а копия SXM2 → PCIe
> задерживала следующий микробатч SXM2. Теперь входящая загрузка идёт в своём
> потоке и ждёт только освобождения своего слота, а исходящая копия сначала
> быстро кладётся в кольцо на той же карте и уходит из другого потока. Внутри
> батча теслы работают без пауз. +8% префила.
>
> **Драфт при прогоне промпта.** MTP-драфт должен пройти по всему промпту, чтобы
> заполнить свой KV-кеш, и это стоило 15–20% префила:
> - считает только K и V — внимание, MoE и выходной слой для этих токенов никто
>   не читает (было 2.8 с на 30 тыс., стало доли секунды);
> - `eh_proj` одной матрицей вместо 512 маленьких;
> - скрытое состояние основной модели передаётся драфту прямо на устройстве, а не
>   туда и обратно через RAM по x4-линку (`LLAMA_MTP_STAGE`), и лишняя копия
>   этих 165 МБ при конвертации батча убрана;
> - прогон батча откладывается до запуска следующего батча основной модели, чтобы
>   она не останавливалась на каждом батче (`LLAMA_MTP_DEFER`). Буфер состояний
>   двойной, строка переноса копируется на устройстве, половины защищены
>   событиями; сервер сбрасывает отложенную работу перед чекпоинтами, кешем
>   промптов и правкой KV.
>
> **Точный top-k для индексатора QSA.** Разреженное внимание оставляет ~2 тысячи
> позиций из десятков тысяч на токен, и V100-сборка (в её CUB нет `DeviceTopK`)
> делала это полной сортировкой каждой строки. Новое ядро: radix-select порога,
> все элементы выше него и равные ему по возрастанию индекса, битонная
> сортировка отобранных. Результат — ровно первые k той же стабильной
> сортировки. Для шага генерации (4 длинные строки) строка раскладывается на
> много блоков. Префил +2–6%, генерация после длинного промпта +10–20%.
>
> ### Генерация: драфт дешевле, сэмплинг на карте
>
> - **Выходной слой драфта по 53 тысячам токенов** вместо 248 тысяч (вся
>   кириллица и частые латинские): 644 → 138 МБ чтения на каждый черновой
>   токен. Черновик всё равно проверяет основная модель, поэтому вывод не
>   меняется. Первый вариант — «первые 64 тысячи id» — убил русский: у Qwen3.5
>   русские слова лежат в id выше 150 тысяч. +5–7%.
> - **Сэмплинг на карте** (`-bs`) и быстрое ядро top-k для малых k: на хост
>   уходят 10 кандидатов, а не 4 × 248 тысяч logits.
> - **ngram-mod перед MTP** (`--spec-type ngram-mod,draft-mtp`): когда текст
>   повторяет уже написанное (правки файлов, цитаты), черновик до 64 токенов
>   берётся из контекста. +20% на таких ответах, на остальных ничего не стоит.
> - Входы графа грузятся раньше активаций (`GGML_SCHED_INPUTS_FIRST`), ядро
>   `get_rows` для строк из одного элемента — мелочи по 0.5–2%.
>
> ### Точность
>
> Почти всё здесь побайтово сохраняет вывод: совпадают greedy-хэши, хэши
> сэмплинга с фиксированным seed и счётчики принятых черновых токенов до
> токена; отдельно прогнан сценарий с многоходовым диалогом, кешем промптов,
> обрывом запроса посреди префила и восстановлением чекпоинта.
>
> Два исключения, и оба — не приближения, а другой порядок тех же вычислений:
> - `LLAMA_KV_PAD_PREFILL` и `LLAMA_SERVER_CKPT_OFFSETS` меняют форму
>   микробатчей. KLD против эталона 0.0134 — ровно столько же, сколько даёт
>   штатная сборка с микробатчем 1024 вместо 512 (0.0141); это собственный
>   «шум округления» модели, у которой индексатор QSA отбирает блоки по порогу.
> - ngram-mod меняет ширину проверочного батча там, где срабатывает. HumanEval
>   156/164 при 160 у предыдущей сборки и 157 у исходной: перекидываются одни и
>   те же спорные задачи, сломанных ответов нет. Perplexity не меняется.
>
> ### Что отвергли
>
> - **Прогон драфта в отдельном потоке** — хост освобождался, но PCIe-тесла и
>   так была узким местом: 0%.
> - **Драфт на 5070 Ti** — не помещается (1.8 ГБ при контексте 160 тысяч).
> - **Меньше экспертов в драфте, длина черновика по уверенности (`p-min`)** —
>   без выигрыша или хуже фиксированных трёх токенов.
> - **Слияние выбора экспертов (topk-moe fusion)** — +1%, но меняет округление.
> - **4 слота копий, шаг KV 8192/16384, микробатч драфта 4048, приоритет потока
>   драфта** — ноль, медленнее или OOM.
>
> Полный журнал с числами, профилями и отказами — `~/llama.cpp/bench/perf-log-2026-09-28.md`
> на рабочей машине; все флаги с пояснениями и замерами — в пусковых скриптах
> Flash-Next.
>
> ## Flash-Next, сентябрь 29–30: длинный контекст и тензорные ядра V100
>
> Следующий заход начался с профиля генерации на коде при промпте 10 и 100 тысяч
> токенов. Шаг проверки (4 токена) занимал 42 и 57 мс, карты работают строго по
> очереди, и 70% шага — две теслы. Всё, что росло с контекстом, оказалось
> разреженным вниманием QSA: индексатор и FlashAttention. Затем тот же разбор
> сделали для префила, где после внимания главными стали эксперты MoE на V100.
>
> Числа ниже взяты из разных замеров: у каждого пункта свои «до» и «после» на
> одном и том же промпте. Сводно по генерации на коде (промпт из исходников форка,
> 400 токенов, greedy) и префилу:
>
> | | было | стало |
> |---|---:|---:|
> | генерация после промпта 100 тыс. | 58.5 т/с | **64.3 т/с** |
> | генерация после промпта 30 тыс. | 79.7 т/с | **81.5 т/с** |
> | префил, промпт 10 тыс. | 1782 т/с | **1922 т/с** |
> | префил, 32 тыс. | 1728 т/с | **1838 т/с** |
> | префил, 100 тыс. | 1481 т/с | **1730 т/с** |
> | префил, 150 тыс. | 1305 т/с | **1587 т/с** |
>
> ### Генерация: внимание QSA перестало расти с контекстом
>
> **Пропуск закрытых маской тайлов** в ядрах FlashAttention (tile и vec). QSA
> оставляет каждому запросу ~2 тысячи ячеек, а ядро читало и перемножало все
> тайлы K/V и только потом прибавляло маску −∞. Тайл, который маска закрывает для
> всех запросов блока, добавляет точные нули: максимум не меняется, его множитель
> `expf(0) = 1`, вероятности `expf(−∞) = 0`. Теперь такой тайл пропускается целиком
> после голосования потоков блока. Генерация после 100 тысяч: 25.4 → 27.4 т/с.
> (Идея подсмотрена у проекта Strata; их «компактное» внимание мы отвергли раньше,
> потому что оно меняет порядок сложения, а пропуск нулевых тайлов — нет.)
>
> **`get_rows` для узких строк первым.** Развёртка оценок блоков индексатора в
> оценки ячеек собирает 100 тысяч строк по 4 float, и векторный путь брал их по
> блоку на строку. Ядро «поток на строку» теперь проверяется раньше. 27.4 → 29.2 т/с.
>
> **Сжатые ключи индексатора без копий.** Индексатор на каждом шаге заново
> усредняет ключи по блокам всего контекста. Четыре слагаемых сначала копировались
> через `ggml_cont`, хотя сложение умеет читать срезы по страйдам. Сумма та же,
> копии ушли: 58.5 → 60.6 т/с на 100 тысячах.
>
> **Перевод KV в f16 только там, где его прочтут.** С кешем q8_0 ядро tile (проверка
> на V100) и разреженная сборка MMA (RTX) на каждом вызове переводили в f16 **весь**
> K и V слоя — ~0.3 мс на слой при 100 тысячах — и потом читали около 40% этого.
> Теперь для ≤32 запросов предварительный проход переводит только тайлы, которые
> видит хоть один запрос, плюс хвостовой тайл и ячейку 0 (на неё разреженная
> сборка ссылается при заполнении). Арифметика та же, что у полного перевода, а
> остальное ядро не читает. Для плотного MMA не включается: оно подгружает тайл
> до проверки маски. На вызов: V100 0.31 → 0.13 мс, RTX 0.39 → 0.20 мс; генерация
> 60.6 → 64.3 т/с. Выключатель — `GGML_CUDA_FATTN_LIVE_F16=0`.
>
> Всё в этом блоке сохраняет вывод побайтово: совпадают хэши на промптах 30 и 100
> тысяч, проверочный набор и счётчики принятых черновых токенов.
>
> ### Префил: разреженное внимание на V100
>
> На 100 тысячах FlashAttention занимал 32% времени теслы в префиле, а у RTX почти
> не рос. RTX (Turing и новее) берут разреженную сборку из основной ветки
> llama.cpp: каждая группа из 8 запросов читает только объединение своих видимых
> ячеек. У Volta был только плотный вариант. Широкий разреженный вариант (8
> запросов × 8 голов, 64 столбца) подходит под фрагменты Volta, и теперь теслы
> используют его для батчей промпта, начиная примерно с 33 тысяч ячеек
> контекста. Префил 100 тыс.: 1481 → 1730 т/с, 150 тыс.: 1305 → 1587. Выключатель —
> `GGML_CUDA_FATTN_VOLTA_SPARSE=0`.
>
> По дороге нашлась ошибка самого форка. Флаг «лимит разделяемой памяти для ядра
> уже поднят» лежал в static-переменной шаблонной функции, а динамический
> линковщик делает такой символ общим для RTX- и V100-библиотек. RTX поднимал
> лимит для своего ядра, V100 пропускал `cudaFuncSetAttribute` для своего — и запуск
> падал с нулевой занятостью. Теперь лимит помнится по указателю на ядро.
>
> ### Префил: эксперты MoE на тензорных ядрах V100
>
> После внимания в префиле тесл ~43% времени заняли эксперты. У Volta нет
> целочисленных тензорных ядер, поэтому MMQ считал их на DP4A. Новое ядро
> (`ggml-cuda/mmid-tc.cu`) распаковывает веса экспертов в f16 и умножает на
> FP16-тензорных ядрах (WMMA, накопление в f32). Веса каждой строки подгружаются в
> разделяемую память целым суперблоком (k-кванты) или четырьмя блоками, следующий
> кусок читается в регистры, пока считается текущий. Поддерживаются Q4_K, Q5_K,
> Q5_1, Q8_0, батчи от 64 токенов. Выключатель — `GGML_CUDA_MMID_TC=0`.
>
> На вызов при формах Flash-Next (512 экспертов, 512 токенов): Q4_K 1600 → 1540 мкс,
> Q5_1 2690 → 1860, Q8_0 2770 → 2290, Q5_K без изменений. Префил: 10 тыс.
> 1782 → 1922 т/с, 32 тыс. 1728 → 1838. Выигрыш дали два шага: чтение строк
> непрерывными кусками вместо 128 разбросанных кусочков по 32 байта и снятие
> ограничения регистров, из-за которого переменные уходили в локальную память. До
> предела по чтению весов ещё примерно в 2.5 раза.
>
> ### Драфт с точными весами
>
> Не-экспертные матрицы MTP-слоя (внимание, `eh_proj`, гиперсоединения, общий
> эксперт) переквантованы в Q8_0 из BF16-чекпойнта вместо Q4_K. Это ещё одна идея
> Strata. Доля принятых черновых токенов в чате выросла на ~1 п.п., генерация —
> на 0.5–1%, цена — 38 МиБ на PCIe-тесле. Вывод основной модели от драфта не
> зависит.
>
> ### Точность
>
> Два изменения меняют арифметику и поэтому проверялись на качество.
> - **Разреженное внимание на V100.** KLD на коде при контексте 64k —
>   0.0137, top-1 совпадает на 98.2%, perplexity на 0.2% ниже. Одна только смена
>   микробатча с 512 на 1024 на той же длине даёт 0.053 и +2.2% perplexity: QSA
>   каскадом перекидывает выбор блоков от любой смены округления. HumanEval с
>   контекстом 40k: 154 → 156 из 164.
> - **Эксперты на тензорных ядрах.** Активации идут в f16, а не квантуются в q8.
>   KLD при 8k — 0.0053 (смена микробатча — 0.0141), perplexity −0.03%, HumanEval
>   156/164 без единой изменившейся задачи.
>
> ### Qwen3.8-27B
>
> Проверка 27B на новой сборке нашла регрессию: префил на 60 тысячах упал с 594 до
> 562 т/с. Причина — пропуск закрытых тайлов в плотном MMA-ядре Volta. С
> причинной маской пропускать там нечего, а голосование на каждом тайле стоило
> синхронизации. После разреженного пути на V100 до этого ядра не доходят и
> длинные промпты Flash, так что голосование из MMA убрано: 27B вернулась к
> 594 т/с, у Flash префил на 22 тысячах 1716 → 1764. Вывод 27B побайтово тот же,
> что до всех работ этой недели. Эксперты на тензорных ядрах 27B не касаются: она
> плотная.
>
> ### Что отвергли
>
> - **Порог уверенности драфта `p-min` 0.3 и 0.5** (у Strata 0.5): медленнее на
>   всех замерах.
> - **Окно внимания драфта на последние 32 тысячи** — ~1.6% шага на 100 тысячах, не
>   стоит сложности.
> - **Микробатч 1024** — нехватка памяти на 5080 при контексте 160 тысяч.
> - **Экспертное ядро с подгрузкой следующего шага в регистры и с одним блоком на
>   SM без лимита регистров** — оба медленнее.
>
> Куда уходит время сейчас. Префил на 100 тысячах: на теслах эксперты ~43%,
> внимание 18–20%, top-k и GDN по 5%, а RTX простаивают три четверти времени. Шаг
> генерации — около 42 мс, из которых ~5 мс карты простаивают, пока хост готовит
> следующий шаг.

## Quick start

A few options to get `llama.cpp` installed on your machine:

- Visit https://llama.app and follow the instructions
- Run with Docker - see our [Docker documentation](docs/docker.md)
- Download pre-built binaries from the [releases page](https://github.com/ggml-org/llama.cpp/releases)
- Build from source by cloning this repository - check out [our build guide](docs/build.md)

Once installed:

```sh
# Download and run a model directly from Hugging Face
llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF

# Launch OpenAI-compatible API server
llama serve -hf ggml-org/Qwen3.5-0.8B-GGUF
```

## Description

The main goal of `llama.cpp` is to enable LLM (and VLM) inference with minimal setup and state-of-the-art performance on
a wide range of hardware - locally and in the cloud.

- Plain C/C++ implementation without any dependencies
- Apple silicon is a first-class citizen - optimized via ARM NEON, Accelerate and Metal frameworks
- AVX, AVX2, AVX512 and AMX support for x86 architectures
- RVV, ZVFH, ZFH, ZICBOP and ZIHINTPAUSE support for RISC-V architectures
- 1.5-bit, 2-bit, 3-bit, 4-bit, 5-bit, 6-bit, and 8-bit integer quantization for faster inference and reduced memory use
- Custom CUDA kernels for running LLMs on NVIDIA GPUs (support for AMD GPUs via HIP and Moore Threads GPUs via MUSA)
- Vulkan and SYCL backend support
- CPU+GPU hybrid inference to partially accelerate models larger than the total VRAM capacity

The `llama.cpp` project is build on top of the [ggml](https://github.com/ggml-org/ggml) library.
